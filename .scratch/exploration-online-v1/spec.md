# Spec: 探索内容上云 v1（exploration-online-v1）

## Problem Statement

局外经济已全量上云（v1 仓库同步、v2 局外状态、v3 账号体系），服务器是局外状态的唯一真源。但局内探索的内容——每个箱子装什么、哪些敌人点生成什么队伍、出生/撤离点选哪个——仍由客户端本地随机生成：雾里藏着什么只有客户端自己知道，服务器无法对账，作弊面与"换设备即失真"的问题和上云前的局外一样。需要把探索内容的**生成权与所有权**移到服务器，同时不能牺牲手感：网络再差，移动也不能卡。

## Solution

服务器在开局时生成并持有全图内容，作为唯一权威。客户端用服务器下发的种子在本地**预测摆位**（敌人存在性与威胁等级、箱子存在性）用于即时渲染——雾保持纯演出，渲染永远不等网络。一切后果性交互（撞敌开战、开箱）走请求-响应获取权威数据，超时则拒绝并提示网络异常。

生成算法采用**子种子架构**（每个随机消费点从独立派生种子起步），Go 与 C# 双端各实现一份、以种子向量交叉测试锁死一致性；客户端的预测只是取同一算法的摆位部分。本阶段不引入服务器推送通道，`NetRpc` 保持纯请求-响应——超时拒绝本身就是降级 fallback。

## User Stories

1. 作为玩家，我进入探索时地图内容（箱子、敌人分布）由服务器生成，与我其他局外资产同一信任级。
2. 作为玩家，网络正常时我感受不到任何联网痕迹：进房雾散、敌人已在、箱子可开，与单机无异。
3. 作为玩家，网络差时我的移动永远不被卡住，只是开箱或撞敌会被拒绝并提示"网络延迟较大"，网络恢复后可继续游戏。
4. 作为玩家，我断线重连后回到同一局：开过的箱子还开着，没打的敌人还在，不必重开。
5. 作为玩家，我开箱获得的物资与服务器记录一致，结算时不会出现对不上的账。
6. 作为玩家，我撞上敌人即进入战斗，战斗队伍构成由服务器提供，与本地渲染的威胁等级一致。
7. 作为玩家，我在房间之间穿行时，敌人的存在与否在两个设备上是一致的（同一种子同一种摆位）。
8. 作为开发者，我想让服务器成为探索内容的唯一生成者与持有者，客户端只做渲染与交互上报，以便结算可对账。
9. 作为开发者，我想让生成算法双端同构（Go 生产 / C# 场景调试与预测）并经种子向量交叉测试，以便预测永不漂移。
10. 作为开发者，我想让交互请求按 (runId, pointId) 幂等，以便网络重试不会双拿或双扣。
11. 作为开发者，我想让 start_run 幂等（已有活跃 run 则返回现状），以便断线重连的恢复路径不引入第二套消息。
12. 作为开发者，我想让每个随机消费点从独立子种子起步，以便双端实现互不重放随机流、摆位可独立推演。
13. 作为开发者，我想让客户端既有的战斗侧随机源保持不动，以便战斗内核的确定性测试与既有行为零影响。
14. 作为开发者，我想让敌人摆位必须归属房间成为硬性不变量（导出与生成两处校验、违反即报错），以便房间始终是完整的内容单元。
15. 作为开发者，我想让服务器配置面与客户端同源（同一批导出 JSON 经 sync_config 同步），以便生成逻辑两端读到的数据完全一致。
16. 作为开发者，我想让结算对账覆盖开箱所得（带出物资 ⊆ 开箱所得 ∪ 携带入场 ∪ 战斗所得），以便物资来源可审计。
17. 作为开发者，我想把保密性取舍记录在案并预留切换路径，以便未来需要摆位保密时不用重做交互层。
18. 作为开发者，我想让大厅的种子输入退役（种子一律服务器分配），以便本局身份只有一个权威来源。

## Implementation Decisions

**职责边界**

- 服务器拥有：本局内容生成与持有（箱子物品清单、敌人存在性/威胁/队伍、出生与撤离点选择）、交互校验与消耗记账、结算对账。
- 客户端拥有：场景渲染与雾演出、摆位预测渲染、交互上报；战斗模拟与战斗侧随机（AI/逃跑/掉落）不变，仍走既有本地随机源。
- 客户端具备完整生成能力（同种子可复现全图），但正常流程只消费摆位结果用于渲染；箱内物品与敌人队伍构成只在交互响应中由服务器下发。

**协议 v4（沿用 JSON 信封 + rid，新增三条消息）**

- `start_run {difficulty}` → ok `{runId, seed, spawnPoint, extractionPoint}`。服务器选种子。**幂等**：该 uid 已有活跃 run 时返回该 run 现状（含已消耗点集合）——这就是断线重连的恢复路径，不另设 resume 消息。出生/撤离点显式下发，不参与预测（开局即刻要用，且消除两处漂移风险）。
- `encounter {runId, pointId}` → ok `{enemyPartyId, threat}`。服务器校验该点在本局确实生成了敌人；重复请求返回相同结果（幂等）。
- `loot {runId, pointId}` → ok `{itemIds}`。首次成功即标记该点已消耗；重试返回相同清单（幂等）；校验该点存在且有剩余。
- `settle` 扩展对账：带出物资须 ⊆（开箱所得 ∪ 携带入场 ∪ 战斗所得）。战斗所得本阶段信任客户端上报——战斗内核上云前的既定架构边界。
- 错误语义复用既有错误码体系：point 不存在/已消耗、无活跃 run、活跃 run 冲突等。
- **超时即 fallback**：客户端对 encounter/loot 设超时，超时按拒绝处理并提示"网络延迟较大，请检查网络连接"；断线走既有重连与会话恢复，不做新机制。移动与渲染永远不因网络阻塞。

**子种子与可移植随机**

- 每个随机消费点从独立子种子起步：`subSeed = hash(masterSeed, kind, index)`，kind ∈ {resource, enemy, extraction, spawn}；resource 内每个物资点再按自身 index 派生。
- 生成用 PRNG 选一个双端易精确实现的小算法（SplitMix 系量级），Go 与 C# 各一份实现。
- 客户端既有战斗侧随机源（System.Random 体系）完全不动；其种子改为采用服务器下发的 masterSeed，保持审计一致。

**生成器同构（一套算法、双端各一份）**

- Go 版为生产实现（服务器生成全图内容）；C# 版供编辑器场景调试与客户端摆位预测。预测 = 取同一算法的敌人摆位与箱子存在性 stage，不是第二套逻辑。
- 现有顺序流消费的客户端生成器重构为子种子结构；重构后双端在相同 (masterSeed, 配置) 下输出逐位一致，由种子向量测试保证。
- 场景调试 fallback 保留：未经 start_run 直接进图时，用本地种子跑 C# 版生成器（编辑器调试专用，不要求与服务器一致）。

**客户端装配**

- 固定布局（房间矩形、各类点位）来自 MapDefinition 资产（客户端本来就要用它渲染房间与雾）；摆位来自本地预测；出生/撤离点用 start_run 显式值。雾保持纯演出（进房即散），不与数据到达绑定。
- 大厅战备的种子输入退役：本局种子一律由服务器分配。

**服务器配置面（与客户端同源）**

- sync_config 增补 tbresourcepointconfig、tbenemypartyconfig（生成需要掉落权重与队伍池），沿用"直接读 gen_cli 导出 JSON"的既定决策。
- MapDefinition 导出管线：编辑器菜单把地图资产序列化为 JSON 进 DataTables，随 sync_config 进服务器 config；服务器据此重建固定布局。
- **房间归属不变量：每个敌人点必须归属某个房间（roomIndex ≥ 0）**。校验两处——编辑器导出时与服务器生成时；违反直接报错，不做静默处理。

**会话生命周期**

- 单用户单活跃 run，服务器内存态即可（崩溃丢局可接受，与原型阶段匹配）。
- settle 是唯一终结路径（撤离/死亡都是 outcome）；消耗记账随 run 存续，重连恢复后依然有效。
- 超时未结算的 run 由 TTL 清理，防泄漏。

**保密性取舍（记录在案）**

- 客户端持种子即具备推演全图摆位的能力（箱子存在性、敌人摆位可被内存读取）；箱内物品与队伍构成仍保密。单机阶段接受此取舍。
- 交易完整性不受影响：所有"取得"动作经服务器逐次校验，知道摆位也拿不走清单外的东西。
- **切换路径**：未来需要摆位保密时，从 start_run 响应撤掉 seed，渲染源从"预测"切到"按房推送"，交互协议不变——预测与推送是同一交互层上可互换的表现策略。此前讨论的迷雾三态/禁交互方案即该路径的实现底稿，不丢弃。

## Testing Decisions

- 只测外部行为：给定 (seed, 配置) 的生成输出、协议消息往返、幂等与冲突语义；不测内部数据结构。
- **种子向量交叉测试**（本特性的核心回归锚）：一组固定 (masterSeed, MapDefinition, 配置) 向量，Go 与 C# 测试各自断言完全一致的摆位输出（敌人存在性/威胁等级/队伍选择、箱子存在性、出生/撤离点）；向量常量在两侧测试中逐字一致。
- Go 侧：生成器纯函数表驱动测试（先例：itemtable / core.apply 的表驱动测试）；fake WS 客户端走 start_run→encounter→loot→settle 全流程（先例：server_test 的 fake 客户端模式），覆盖幂等重试、point 不存在/已消耗、活跃 run 冲突、TTL 清理。
- C# 侧：EditMode 生成器测试改为种子向量断言（现有 MapBuilder 生成测试的顺序流注入方式随子种子重构调整）；EditMode 全量回归保持绿。
- 人工验收（用户回填）：Play Mode 下正常流程手感无感；人为劣化网络（加延迟/断网）时拒绝提示出现、恢复后可继续；断线重连续局正确。

## Out of Scope

- 战斗内核上云与战斗结果/掉落校验（胜负与战斗所得仍客户端上报）。
- 服务器主动推送通道（无 rid=0 push 消息）；预取邻房等延迟优化。
- 房间三态/禁交互式迷雾 fallback（被预测方案取代；作为保密性切换路径的实现底稿记录在案）。
- 箱子存在性随机化的实际权重配置（预测管线就绪，本轮箱子仍全量生成，参数另调）。
- 玩家位置上报与房间归属的服务器侧校验（单机阶段信任客户端）。
- 程序化地图拓扑生成（布局仍是固定手工地图，随机只在内容层）。

## Further Notes

**决策沿革**（四轮讨论，供回溯）：

1. 最初两案：只发种子客户端自算（天花板低：服务器无内容状态，无法对账）vs 服务器持有内容+交互回传（交互时刻有 RTT）。
2. 引入进房推送以隐藏交互延迟 → 发现需新建推送通道与房间三态机制。
3. 讨论网络劣化 fallback：锁门 vs 迷雾三态禁交互（结论：锁交互不锁移动）。
4. 终案：摆位预测 + 交互权威。预测让渲染不等数据，交互权威由请求-响应本身承担，推送通道与迷雾三态整体退场，协议反而最简。

**关键代码事实**（讨论中确认，实施时以此为前提）：

- 现有生成器已是纯函数（配置 + 随机源进，结果数据出，不碰 Unity 对象），Go 移植是机械翻译。
- MapDefinition 为固定布局：物资点每局必刷（箱子存在性当前恒真）、敌人点存在性随机（威胁 roll 可为 None）、出生/撤离点为候选列表随机选取。
- 敌遭遇为碰撞触发（撞上实体立即开战），故敌人摆位必须预测（含威胁等级——prefab 按威胁选取）；箱子无碰撞依赖，内容等 loot 响应即可。
- 服务器消息集现状：register/login/auth/pull/migrate/settle/ops/history；settle 已携带 seed 字段（v2 引入），本 spec 将其语义升级为"本局主种子"。
- 客户端随机源接口为单一接缝，战斗侧继续使用；内容生成切换到子种子 PRNG 后两者互不干扰。
