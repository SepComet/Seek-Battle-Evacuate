# Spec: 仓库上云 v1（warehouse-online-v1）

## Problem Statement

SBE 目前是纯单机：局外经济数据（仓库物品与布局、角色花名册与穿戴装备）以明文 JSON 存在玩家本机，进度绑定单台设备，无法为后续的账号体系、商店、多设备等在线能力铺垫，也没有服务器侧的审计与防丢档手段。需要在不改动局内玩法（探索/战斗/撤离）的前提下，把局外经济数据搬到自建服务器。

## Solution

第一版联网：自建 Go 单进程服务端 + MySQL，通过 WebSocket（JSON 消息）通信。客户端强制在线，以匿名设备账号登录；服务器成为局外经济数据的唯一真源；局内探索与战斗完全保留在客户端本地。每次对局结束（撤离成功/团灭/超时/主动放弃）以"局内增量（delta）+ runId 幂等"上报结算，服务器做轻度合法性校验后落库，并返回权威仓库快照刷新客户端。大厅内的装备穿卸、仓库布局整理走独立的服务器操作。存量本地存档在首次登录时自动迁移上云，之后本地文件降级为只读缓存。

## User Stories

玩家视角：

1. 作为玩家，我首次启动游戏时自动获得一个匿名账号（无需注册），以便直接开始玩。
2. 作为玩家，我再次启动游戏时自动沿用上次的身份登录，以便仓库进度延续。
3. 作为玩家，我登录后看到的仓库与我上次退出时完全一致，以便服务器成为我进度的可靠真源。
4. 作为玩家，我在局内的探索与战斗体验与单机版完全一致，以便联网改造不破坏玩法手感。
5. 作为玩家，我撤离成功后，背包与保险箱里的物资进入仓库并持久保存，以便战利品不丢。
6. 作为玩家，我团灭或超时后，保险箱物资入库、背包物资损失、角色穿戴装备销毁，以便风险规则与单机版一致。
7. 作为玩家，我主动放弃当局也按失败结算（背包照丢），以便不能靠放弃按钮保住背包。
8. 作为玩家，我局中异常退出（崩溃/强关）后这局视为没有发生，仓库回到开局前状态，以便不产生半截账。
9. 作为玩家，结算上报时断线，游戏停在结算界面自动重试直至成功，以便战利品不因网络抖动丢失。
10. 作为玩家，重试导致同一局结果被重复发送时不会多拿或少拿物资，以便幂等可靠。
11. 作为玩家，我在大厅穿/卸装备立即生效且被服务器记录，以便装备状态不会两处不一致。
12. 作为玩家，我整理仓库格子后关闭仓库界面，布局被服务器记住，以便下次登录布局还在。
13. 作为玩家，我在局内招募的角色在结算后进入服务器侧花名册，以便阵容进度持久。
14. 作为玩家，大厅断线时仓库/装备/开局等会改经济数据的按钮置灰，以便我不会做出服务器记不住的操作。
15. 作为玩家，局内断线不影响我继续玩完这一局，以便网络抖动不打断体验。
16. 作为玩家，我已有的本地存档在首次联网登录时自动上传成为服务器初始数据，以便不损失现有进度。
17. 作为玩家，客户端始终以服务器返回的权威快照为准刷新，以便不出现本地/服务器状态分叉。

开发者视角：

18. 作为开发者，我想让局内代码（探索/战斗/撤离/拾取）零改动，以便联网改造不引入玩法回归。
19. 作为开发者，我想让所有经济写操作经过同一个同步命令层并产出服务器操作（op），以便上报逻辑只有一份、可审计。
20. 作为开发者，我想让客户端只依赖一个连接接口而不是具体 WebSocket 库，以便测试用假连接、将来可替换传输。
21. 作为开发者，我想让每条协议消息携带版本号字段，以便将来灰度升级协议。
22. 作为开发者，我想让服务器对上报做轻度校验（物品 ID 存在、堆叠数量合法、稀有度枚举合法），以便脏数据不入库。
23. 作为开发者，我想让校验用的配置表由 Luban 从同一份源表生成给 Go，以免客户端与服务器两套配置漂移。
24. 作为开发者，我想让结算处理是单数据库事务 + runId 唯一键，以便幂等语义可证明。
25. 作为开发者，我想让 delta 的构造与应用在两端都是纯函数，以便单测覆盖合并语义。
26. 作为开发者，我想保持内存存档根对象（SaveData）的形状不变，以便全工程既有读路径免改。
27. 作为开发者，我想让本地缓存写入仍走原子写（临时文件+改名），以便断电不损坏缓存。
28. 作为开发者，我想让四种对局结局（撤离/团灭/超时/放弃）都走同一条结算路径，以便结算语义只有一份。

运维视角：

29. 作为运维者，我想用单个 Go 二进制 + 一台 MySQL 部署整个服务端，以便朋友规模开服成本最低。
30. 作为运维者，我想让服务器保存每局结算记录（runId、结局、时间），以便出现刷装备纠纷时可审计。
31. 作为运维者，我想让服务器重启不丢任何玩家数据，以便重启窗口无成本。

## Implementation Decisions

**总体架构**

- 服务端：Go 单进程 + MySQL，WebSocket 通信，服务器在两次消息之间完全无状态（不跟踪"进行中的一局"）。
- 客户端：局内玩法零改动；改造集中在持久层、结算流程与大厅经济写操作。
- 部署：内网明文 ws；将来公网在前面挂反向代理做 wss，Go 代码不感知。

**网络与协议**

- 传输：WebSocket；客户端用 websocket-sharp，服务端用 gorilla/websocket。
- 消息格式：JSON 信封 `{ t: 类型, v: 协议版本, ...payload }`；网络 DTO 用 Newtonsoft 序列化（客户端存档序列化维持 JsonUtility 不动）。
- 客户端网络层只暴露一个连接接口（IServerConnection），websocket-sharp 是其唯一实现；测试用假连接。
- 消息清单（v1 契约）：
  - 客户端→服务器：`register(deviceUuid)`、`auth(token)`、`pull`（拉全量经济快照）、`migrate_upload`（首登迁移上传）、`settle(runId, outcome, ops...)`（结算对账）、`move_batch`（布局批量调整）、`equip` / `unequip`。
  - 服务器→客户端：`auth_ok(token, snapshot)`、`settle_ack`（权威快照或已应用操作+新铸 UID）、统一错误码。

**账号**

- 匿名设备账号：客户端首次启动生成并持久化设备 UUID；`register` 换取 token，之后凭 token 认证。
- 不做账号密码、第三方登录、多设备绑定。

**数据边界（服务器拥有什么）**

- 上云：仓库物品、仓库布局、角色数据（花名册 + 穿戴装备）。原则：凡在局内会产出/消耗/损毁的资产归服务器。
- 留本地：loadout（带谁/难度/携带计划，属"意图"非资产）、runHistory（战绩，服务器结算表天然含审计数据）、设置类数据。
- 强制在线，服务器唯一真源；无离线模式、无存档合并。

**物品身份与操作模型**

- 物品无词条/随机属性，实例即 `(itemId, count)`；物品配置以 Luban int 主键标识。
- 服务器为每个仓库行铸造稳定 bigint UID；客户端拉快照后持有并引用 UID。装备行用归属状态表达（在仓库/穿在某角色），为将来词条系统预留实例身份。
- delta 为操作集语义：`add(itemId, count)`（新战利品，服务器铸新 UID）、`remove(uid, count)`（消耗/损毁）、`move(uid, x, y, rotated)`（纯布局），外加装备穿卸与花名册操作。

**结算（settle）语义**

- 结算时一次性对账：带入局内消耗的物品、背包（仅撤离成功时）与保险箱（恒定）入库、团灭时装备销毁、局内招募角色入册；开局不上报、不锁定物资。
- 四种结局（Extracted / Defeated / TimedOut / Quit）都产生一次 settle；Quit 按失败处理。
- 局中异常退出：客户端局内状态本就纯内存、存档未动，服务器也未动，两侧天然一致，无需恢复逻辑。
- 幂等：客户端在撤离结算时生成唯一 runId；服务器结算表以 runId 为唯一键，重复上报直接返回上次结果。
- 落地时序：客户端收到服务器 ack 后才写本地缓存；ack 前强退 = 本局作废（战利品放弃，两侧一致）。

**校验（轻度）**

- 服务器持有 Luban 生成的 Go 配置表（新增 gen_server 导出脚本，复用既有 server 目标与 s 表组），校验：物品 ID 存在、堆叠不超上限、稀有度枚举合法。
- 不做产出合理性深校验、不做反作弊（单机局内改内存服务器本就拦不住）。

**客户端改造方式**

- 内存 SaveData 形状不变，全部既有读路径免改；经济写操作改走新的同步命令层（WarehouseSyncService）：更新内存 + 产出服务器操作。
- 持久组件（SaveComponent）职责重定向：从"本地 JSON 为真源"改为"服务器为真源 + 本地原子写缓存"；meta 类数据仍本地落盘。
- 新增登录过程状态（ProcedureLogin），位于资源预载之后、进入大厅之前：设备 UUID → 注册/换 token → 拉快照 → 填充内存 SaveData →（首登）迁移分支。
- 大厅写操作：穿/卸装备即时上报 `equip`/`unequip`；仓库布局在界面关闭时批量上报 `move_batch`（沿用现有"关闭时刷脏"习惯）。
- 断线行为：大厅置灰经济按钮；局内不中断；结算界面卡住重试。
- 迁移：首登检测服务器无此账号数据 → 上传本地经济数据为初始状态 → 服务器标记已初始化 → 本地降级缓存。

**数据库**

- 五张表：`users`（deviceUuid 唯一）、`auth_tokens`、`warehouse_items`（bigint 自增 UID 主键，含 x/y/is_rotated 布局列与装备归属状态列）、`user_characters`、`settlements`（runId 唯一，幂等 + 审计）。
- 访问用 database/sql（至多加 sqlx），不用重 ORM；建表走迁移脚本。

**将来方向（本期只留口子）**

- 货币/商店系统上线时直接做在服务器侧，不经过本地存档。
- 协议版本号字段为灰度升级预留。

## Testing Decisions

- 只测外部行为，不测实现细节：客户端断言"经济意图 + 假连接的消息序列 → 内存 SaveData 状态与发出的操作序列"，不断言私有字段；服务端断言"操作集 + 输入状态 → 输出状态或校验错误"。
- 客户端唯一新接缝：同步命令层 + 连接接口的假实现（EditMode NUnit，沿用既有 EditMode 测试套件的位置与风格，先例为容器、局会话、主玩法 FSM 的现有测试）。
- 覆盖链路：登录拉仓 → 穿/卸装备 → 开局 → 四种结局的结算 delta → 断线重试 → 权威快照回填 → 同 runId 重发幂等。
- 复用既有接缝：主玩法 FSM 的 EditMode 测试扩展（settle 状态经假连接同步后落缓存）；容器与局会话的既有测试不动。
- 服务端两条：delta 应用器/校验器为纯函数做 Go 单测；一条集成测试（docker 起 MySQL + 真 WebSocket 服务）走全流程：注册 → 迁移 → 结算 → 幂等重发。
- 不测：WebSocket 库本身、MySQL、UGF 框架、UI 渲染。
- 遵守项目验证纪律：agent 不启动 Unity、不执行编译；需占用 Unity Editor 的 EditMode 验证由用户执行并回填结果。

## Out of Scope

- 局内任何联网化：战斗同步、多人协作、服务器权威局内逻辑。
- 反作弊深校验（产出合理性、行为检测）与 token 之外的风控。
- 账号密码、第三方登录、多设备绑定与存档合并。
- 离线模式。
- 货币与商店（客户端 ShopForm 仍按原 TODO 推进；经济数值届时直接落服务器侧）。
- 词条/随机属性系统及其物品实例模型（UID 模型已为其预留）。
- runHistory 上云（本地保留；服务器结算表已含审计数据）。
- 公网部署运维（域名、TLS、监控、多实例）——设计已预留（消息版本号、反代 wss），本期不实施。

## Further Notes

- 工作量估算（单人、熟悉 Unity 与 Go，纯开发口径）：客户端 8–12 人日、服务端 5–8 人日、联调与部署 2–3 人日；改造比例约 客户端 55% / 服务端 30% / 联调 15%，局内玩法 0%。
- 本 spec 由两轮设计问询（14 项决策）+ 6 项默认小决定综合而来，代码事实基于对 SBE-Client 现状的一次全量探索（存档层、物品模型、撤离结算流程、Luban 工具链）。

## Comments

### 实现后审查记录（2026-10-25，code-review 两轴）

已确认的实现偏差（环境受限，均为可回退决策）：

1. WebSocket 库：gorilla/websocket → Go 标准库手写最小实现（构建环境无外网；`SBE-Server/internal/ws`，有帧/握手/回显测试）。
2. Go 侧配置加载：Luban Go 代码生成 → 直接读取 gen_cli 导出的 `tbitemconfig.json`（同源生成物；`tools/sync_config` 同步）。
3. 网络序列化：Newtonsoft → JsonUtility（协议信封为扁平 camelCase DTO，与存档 DataStruct 惯例一致，JsonUtility 足够，少一个依赖）。
4. 协议消息：spec 中的 `move_batch`/`equip`/`unequip` 统一为单一 `ops` 消息（同一操作集语义，服务器同一分派路径）。

已知限制（接受，待后续 ticket）：

- 大厅断线门控覆盖"开局"与"穿卸装备"入口；仓库布局整理未门控（纯展示性，未上报的调整在下次拉取时以服务器为准纠正）。
- 结算界面不阻塞等待服务器 ack：结算在后台串行重试，ack 前强退 = 本局作废（与 spec 落地时序一致）。
- 稀有度校验不适用：v1 协议消息不携带 rarity 字段，无从校验。
- 无词条实例模型下，"死亡销毁装备"与"同物品新战利品入库"在差分中可能以 rel 语义表达，经济总量等价；引入词条系统时需收紧为按实例身份的 del+add。
- ProcedureMainFsmTests 的 settle-经假连接扩展用例、MySQL store 集成测试（需 docker/本机 MySQL）留待后续。

审查修复（已入库）：ProcedureLogin/M​ainSettlementState 两处编译错误；MySQL rewrite 显式保留 uid（防 AUTO_INCREMENT 重铸导致客户端引用失效）；LoadoutForm 四个穿卸入口补离线门控；SettleAsync 改用可注入延迟；DeviceIdentity 读取失败补 Log.Error；Go 两处 newToken 去重至 store.NewToken。
